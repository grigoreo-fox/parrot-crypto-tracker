# ADR 0001: Представление цены через JavaScript number и SQLite REAL

- Статус: принято
- Дата: 2026-11-04

## Контекст

Сервис получает цены от CoinMarketCap (CMC), сохраняет историю и возвращает цены клиентам. В модели CMC для `quotes/latest` цена описана как JSON `number` с форматом `bigdecimal` ([документация CMC](https://coinmarketcap.com/api/documentation/pro-api-reference/cryptocurrency/quotes-latest.md)). Это не означает, что исходное десятичное значение всегда точно представимо в JavaScript `number`.

Для выбора точности принимаем учебное допущение: конечная цель проекта известна, цены нужны в том числе для отображения **примерных** балансов криптокошелька. Это не требование задания о реализации кошелька, балансов или финансовых операций. Точная десятичная арифметика сейчас не требуется.

JavaScript `number` и SQLite `REAL` используют двоичную плавающую точку. Они не гарантируют точное представление произвольных десятичных дробей; стандартный разбор JSON может округлить цену ещё до записи в БД.

## Варианты

1. **`number` в JavaScript и `REAL` в SQLite.** Простые разбор, хранение, числовые сравнения и SQL-агрегации; значения и результаты вычислений приближённые.
2. **Десятичная строка и SQLite `TEXT` с разбором JSON без потери точности.** Позволяет сохранить исходное десятичное значение, но требует надёжного lossless-разбора и отдельной стратегии числовых сравнений и арифметики. Это усложняет реализацию и может потребовать дополнительных зависимостей или изменения минимальной версии Node.js.
3. **Строка и приближённое числовое значение одновременно.** Сохраняет исходное значение и упрощает приближённые запросы, но усложняет модель и поддержание согласованности.

## Решение

Использовать JavaScript `number` для цены в приложении, SQLite `REAL` для хранения и JSON `number` в ответах нашего API. Применять обычный разбор JSON и не вводить отдельную библиотеку десятичной арифметики или lossless-разбора ради текущих потребностей.

Выбор соответствует числовому формату API CMC и принципу YAGNI: не добавляем сложность для не требуемых сейчас точных вычислений. Формат CMC — не доказательство достаточной точности `number`; приближение принимается сознательно исходя из предполагаемого использования.

Проверять полученную цену как конечное неотрицательное число; отсутствие цены не подменять нулём. Округление для отображения определять отдельно, не меняя сохранённое значение. Допустимость нулевой цены и конкретные правила отображения остаются открытыми.

## Последствия

- Числовые сравнения и SQL-агрегации доступны без преобразования из `TEXT`, но результаты приближённые.
- Исходные десятичные цифры CMC могут быть потеряны при разборе JSON; `REAL` не восстанавливает их. Точных денежных расчётов и равенства дробных результатов гарантировать нельзя.
- API-клиенты получают приближённое JSON-число и должны учитывать собственные ограничения точности. Малые ненулевые цены нельзя бездумно округлять до нуля при отображении.
- Если появятся требования к точным расчётам, потерям не больше заданного предела или сохранению исходных цифр CMC, решение нужно пересмотреть. Понадобятся новая стратегия разбора и хранения, а также миграция ранее сохранённых данных; восстановить уже потерянные цифры невозможно.
