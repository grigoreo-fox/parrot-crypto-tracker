# Архитектура сервиса отслеживания цен

Статус: рабочий черновик. Документ описывает текущие архитектурные решения и открытые вопросы, а не готовую реализацию. Требования и API-маршруты: [PRD.md](./PRD.md); начальная схема БД: [001-initial.sql](./src/database/migrations/001-initial.sql). История существенных решений при необходимости фиксируется в [ADR/](./ADR/).

## 1. Контекст и ограничения

Сервис предоставляет REST API и одностраничный UI для работы с каталогом криптовалют, списком отслеживания и сохранёнными ценами. CoinMarketCap (CMC) — внешний источник данных; SQLite хранит каталог, состояние отслеживания и историю полученных цен.

```text
Пользователь ──> UI в браузере ──┐
                                 ├── HTTP ──> Сервис ── HTTPS ──> CMC API
Другой API-клиент ───────────────┘              │
                                                └──> SQLite-файл
```

Стек задания: Node.js 18+, TypeScript, Express, SQLite с raw SQL, axios, Jest и Supertest; API описывается в OpenAPI 3.0. ORM запрещена. Постоянные данные хранятся в БД, а не только в памяти процесса; файл БД не входит в репозиторий.

Для доступа к SQLite выбран `better-sqlite3`; это дополнительная зависимость, не названная в списке библиотек задания. Её необходимость следует обосновать или уточнить у проверяющих: Node.js 18 не предоставляет встроенный модуль SQLite. Также необходимо проверить минимально необходимые зависимости для сборки, тестирования и документации. Отдельная библиотека логирования не планируется: используем `console.*`.

Ключ нашего API и ключ CMC — разные секреты. Оба поступают через окружение; ключ CMC не передаётся клиентам. `/health` и `/` публичны, остальные маршруты API защищены Bearer token согласно PRD.

## 2. Подход и зависимости

Применяем разделение ответственности (SoC) и SOLID прагматично: в первую очередь единую ответственность (SRP) и инверсию зависимостей (DIP). Внешние механизмы отделяются от сценариев приложения через контракты там, где это полезно; интерфейс не обязателен для каждого класса. Зависимости создаются и связываются при запуске приложения.

```text
HTTP / Express ────────┐
                       ├──> сценарии приложения ──> понятия и правила
Планировщик ───────────┘            │
                                    └──> контракты внешних зависимостей
                                               ↑              ↑
                                       SQLite-репозитории  CMC-адаптер
```

Стрелки обозначают зависимости кода, а не обязательно направление передачи данных при работе. Сценарии не зависят от Express, SQL или формата ответа CMC. Реализации репозиториев и CMC-адаптер выполняют контракты, необходимые сценариям.

Из DDD берём единый словарь и явное выражение подтверждённых правил предметной области. Сложные агрегаты, доменные события и множество bounded contexts заранее не вводим. Структура каталогов и классов определяется по реальным потребностям реализации, а не только по этой схеме.

## 3. Компоненты

| Компонент | Ответственность |
|---|---|
| HTTP-слой | Маршруты, проверка Bearer token, разбор и валидация HTTP-входа, вызов сценариев, преобразование результатов и ошибок в HTTP-ответы. |
| Сценарии приложения | Выполнение действий: управление отслеживанием, чтение цен и истории, синхронизация цен и каталога. Управляют последовательностью операций и применяют согласованные правила. |
| Понятия и правила | Общий словарь и подтверждённые правила работы с валютами, отслеживанием и ценами, независимо от HTTP и SQL. |
| Репозитории | Предоставляют сценариям операции над данными; SQLite-реализации выполняют параметризованный raw SQL. |
| CMC-адаптер | Обращается к CMC через axios, передаёт ключ, задаёт таймаут, проверяет и преобразует ответы и ошибки внешнего API. |
| Планировщик | Управляет расписанием и запусками фоновых сценариев, предотвращает наложение запусков одной задачи и участвует в остановке. |
| Конфигурация | Читает окружение, преобразует и проверяет значения, предоставляет настройки при запуске. |
| Логгер | Единообразно записывает события и ошибки через `console.*` с заданным уровнем логирования. |
| Сборка и жизненный цикл | Создаёт и соединяет компоненты, запускает HTTP-сервер и планировщики, организует остановку и закрытие ресурсов. |

Это разделение обязанностей, а не требование создавать отдельный класс или файл для каждой строки.

## 4. Основные потоки

### Проверка состояния

`GET /health` — публичная проверка HTTP и возможности прочитать таблицу каталога в SQLite: при успехе возвращает `200`, при ошибке БД — `503` без деталей ошибки. Она не проверяет запись в БД, свежесть данных или доступность CMC.

### Чтение сохранённой цены

1. HTTP-слой проверяет запрос и вызывает сценарий чтения.
2. Сценарий получает данные через репозиторий; SQLite-реализация выполняет запрос.
3. HTTP-слой формирует ответ.

CMC в этом потоке не участвует: при его недоступности сохранённые данные остаются доступны, если доступна БД. `latest` читает последнюю сохранённую цену в текущей валюте котировки из ENV и возвращает `null` при её отсутствии; `historical` возвращает накопленные записи с сохранённой у каждой валютой котировки, в том числе прежней. Оба endpoint защищены Bearer token и принимают ID или slug из каталога, в том числе после удаления отслеживания. Допустимая давность цены остаётся открытой.

### Синхронизация цен

1. Планировщик запускает сценарий по настроенному интервалу.
2. Сценарий получает список активных отслеживаемых валют через репозиторий.
3. Сценарий запрашивает цены через контракт источника; CMC-адаптер выполняет внешний запрос.
4. Сценарий передаёт полученные данные репозиторию для сохранения.
5. Планировщик фиксирует результат запуска.

Каталог обновляется отдельным сценарием по отдельному расписанию. Черновой CMC-клиент реализует постраничный `/v1/cryptocurrency/map` и `/v3/cryptocurrency/quotes/latest`; при запросе цен он сам делит ID на последовательные пачки по 250 (это не объявленный лимит CMC). Клиент запрашивает `skip_invalid=true` и возвращает найденные цены вместе со списком отсутствующих ID; при ошибке запроса или некорректном ответе любой пачки частичный результат не возвращается. На реальном API проверено: если в пачке нет ни одного найденного ID, CMC возвращает HTTP 400; такая пачка пока остаётся ошибкой, а не списком отсутствующих ID. Для каталога доступна ручная команда `npm run sync:catalog`: она читает `CMC_PRO_API_KEY` и `DATABASE_PATH`, загружает активный каталог страницами по 100 записей с сортировкой по ID и сохраняет каждую страницу отдельной SQLite-транзакцией через подготовленный upsert. Короткая страница считается последней; записи, отсутствующие в ответе, не удаляются. При сбое сохранённые страницы остаются в БД, а команда завершается с ошибкой. Пагинация по смещению не гарантирует неизменный снимок при изменениях каталога на стороне CMC. При запуске сервера синхронизация пока не выполняется.

Планировщик запускает синхронизацию цен сразу после запуска HTTP-сервера и далее по `PRICE_SYNC_INTERVAL_MS` (по умолчанию 300000 мс); наложение запусков предотвращается в рамках процесса. Если активных валют нет, запрос к CMC не выполняется. Полученные цены и `last_synced_at` сохраняются в одной транзакции; пропущенные CMC ID записываются в предупреждение. При ошибке запроса или некорректном ответе цены этого запуска не сохраняются, ошибка логируется; следующая попытка — по расписанию. Изменившие статус на неактивный во время запроса записи пропускаются при сохранении.

### Добавление отслеживаемой валюты

Маршруты `/v1/cryptocurrency/tracked` защищены Bearer token: `POST` проверяет положительный целочисленный ID и наличие валюты в локальном каталоге, повторное добавление возвращает **409 Conflict**; `GET` возвращает список с пагинацией; `PATCH` приостанавливает или возобновляет отслеживание; `DELETE` удаляет запись отслеживания, сохраняя историю цен. При добавлении CMC не вызывается: цену получает только фоновая задача. SQLite использует подготовленные запросы и ограничение уникальности.

## 5. Данные и валидация

Начальная схема находится в [001-initial.sql](./src/database/migrations/001-initial.sql): CMC ID идентифицирует валюту; каталог, отслеживание и наблюдения цен хранятся отдельно. История сохраняется при удалении из отслеживания. Для каждого соединения приложение включает `PRAGMA foreign_keys = ON`. Начальная схема применяется к пустой БД в транзакции с установкой `PRAGMA user_version = 1`; непустые БД без версии и неподдерживаемые версии отклоняются. Многошаговые изменения, которым нужна атомарность, выполняются в транзакции.

Проверки распределяются по ответственности:

- HTTP-слой проверяет форму и формат запроса, включая запрет одновременно передавать `id` и `slug`.
- Сценарии применяют правила операции; корректный формат ID сам по себе не гарантирует наличия валюты в каталоге.
- Ограничения БД защищают целостность, в том числе при параллельных изменениях.
- CMC-адаптер проверяет и преобразует внешние данные до их использования приложением.

### Представление цены и времени

Цена представляется как JavaScript `number`, хранится в SQLite `REAL` и возвращается JSON-числом. Это сознательный выбор приближённой точности для предполагаемого отображения примерных балансов; точные финансовые расчёты не гарантируются. Подробнее об альтернативах и ограничениях — [ADR 0001](./ADR/0001-price-representation.md). Валюта котировки сохраняется вместе с каждой записью. Приложение проверяет конечность и неотрицательность цены; допустимость нуля и правила отображения остаются открытыми.

В схеме используются временные метки в `TEXT`; точный формат времени в публичном API и семантика отдельных отметок требуют согласования. Конкретный CMC endpoint и его ограничения ещё нужно выбрать и проверить.

## 6. Планировщик и остановка

Приложение рассчитано на один процесс. Интервалы задаются через ENV: ориентиры из PRD — 5 минут для цен и 24 часа для каталога. Планировщик не допускает одновременного выполнения двух запусков одной задачи с помощью состояния внутри процесса; это не защищает от запуска нескольких процессов.

При `SIGINT` или `SIGTERM`:

1. Прекратить планирование новых запусков и очистить таймеры.
2. Немедленно запросить отмену активных задач через сигнал отмены; сценарий передаёт его CMC-адаптеру и не начинает новые шаги после обнаружения отмены.
3. Ожидать обработки отмены **не более 1 секунды**.
4. Организовать закрытие HTTP-сервера и БД и завершение процесса.

Отмена HTTP-запроса и его таймаут — разные механизмы; обязательны оба. Синхронный SQL через `better-sqlite3` нельзя гарантированно прервать сигналом посередине; запись должна сохранять целостность. Ожидаемая отмена при остановке отличается от ошибки CMC.

HTTP-сервер и задача останавливаются одновременно; БД закрывается только после успешной остановки обоих. Если задача не остановилась за секунду, фиксируется ошибка и ненулевой код, БД намеренно не закрывается, пока ею потенциально пользуется задача; принудительное завершение процесса не выполняется. Поэтому момент фактического завершения процесса не гарантирован.

## 7. Конфигурация, ошибки и логи

При запуске модуль конфигурации читает ENV, преобразует значения и проверяет обязательные настройки. Сборка приложения передаёт компонентам только необходимые им значения. Предлагаемая политика: при отсутствующей или некорректной обязательной настройке остановить запуск с понятной ошибкой, не раскрывая секреты.

HTTP-ошибки централизованно преобразуются в безопасные ответы; внутренние детали и секреты не возвращаются клиенту. Ошибки внешнего API, включая таймауты и некорректные ответы, обрабатываются явно. Неуспешное обновление не должно само по себе блокировать чтение сохранённых данных.

Логгер на `console.*` поддерживает уровни `error`, `warn`, `info`, `debug`, `trace` согласно PRD. Компоненты сообщают о значимых событиях; итоговая ошибка фонового запуска фиксируется планировщиком, необработанная HTTP-ошибка — централизованным обработчиком. Избегаем многократного логирования одной и той же ошибки без дополнительного контекста. Секреты и заголовки авторизации в логи не включаются.

## 8. Тестирование

- Сценарии проверяются с подставными реализациями зависимостей: последовательность действий и правила без настоящего CMC.
- SQLite-репозитории проверяются с БД, включая SQL и ограничения целостности; формат тестовой БД определяется отдельно.
- CMC-адаптер проверяется на запросы, преобразование ответов, ошибки, таймауты и отмену без обращения к настоящему CMC.
- Планировщик проверяется на расписание, отсутствие наложения, обработку ошибки и остановку.
- HTTP API проверяется через Jest и Supertest: для каждого endpoint минимум один позитивный и один негативный тест согласно заданию. Нужны также тесты обработки ошибок внешнего API и фоновых задач.

Тесты отдельных компонентов не заменяют проверок совместной работы и выполнения требований задания.

## 9. Открытые решения

- Проверка CMC endpoint на реальном тарифе, квоты и ограничения; подтверждение предварительной политики таймаутов и повторных попыток.
- Семантика частичного сбоя и сохранения частично полученных данных.
- Допустимость нулевой цены и правила её отображения, формат времени, обработка отсутствующей или устаревшей цены.
- Поведение после истечения одной секунды при остановке; порядок закрытия HTTP-сервера и БД.
- Запуск фоновых задач при старте, группировка запросов, детали обновления каталога.
- Пагинация, фильтрация, срок хранения истории и оставшиеся API-ошибки.
- Обоснование дополнительных зависимостей и окончательный способ предоставления OpenAPI-документации.
