# PRD: сервис отслеживания цен криптовалют

**Статус:** рабочий документ, не согласован с Evercode Lab.  
**Источники:** материалы в [`guidlines/`](./guidlines/); исходные PDF имеют приоритет над автоматически извлечёнными Markdown-файлами.

## 1. Как читать документ

- **[Решение]** — решение пользователя для реализации; не обязательно требование Evercode Lab.
- **[Задание]** — прямое требование `Backend_Задание.pdf`.
- **[Материалы]** — практика или формулировка из учебных материалов. Это не обязательно критерий приёмки задания; конкретное задание имеет приоритет при расхождениях.
- **[Открыто]** — вопрос, который источники не определяют или определяют недостаточно.
- **[Предложение]** — возможное решение для обсуждения, не требование заказчика и не принятое решение.

## 2. Цель и границы продукта

**[Задание]** Разработать backend-сервис — REST API для управления списком отслеживаемых криптовалют, получения актуальных и исторических цен и фоновой синхронизации данных через официальный CoinMarketCap API. Сервис хранит историю цен в БД.

**[Открыто]** Под «агрегацией» не определены конкретные вычисления: средние, минимумы, максимумы, интервалы или сводные показатели. Не следует считать их обязательными без уточнения.

**[Открыто]** Не заданы пользовательские роли, число клиентов, нагрузка и требования к развёртыванию в production. Само задание UI не требует; пользователь отдельно решил добавить его.

## 3. Функциональные требования

### 3.1. Доступ к собственному API

- **[Задание]** Аутентификация и авторизация запросов к собственному API — через Bearer token (API Key).
- **[Решение]** Один Bearer token собственного API задаётся через ENV; минимальная длина — 32 символа. Это не ключ CoinMarketCap.
- **[Решение]** `/health` и страница `/` публичны, API защищён. UI позволяет пользователю вручную ввести Bearer token; он хранится только в памяти страницы до перезагрузки и не вшивается в страницу или сборку.
- **[Открыто]** Не определены политика ротации и доступ к документации.
- **[Открыто]** Не задан формат токена и не требуется отдельно регистрация, логин, JWT или OAuth. Bearer описывает способ передачи учётных данных и сам по себе не означает JWT.
- **[Материалы]** В учебном разделе рассматриваются Basic Auth, JWT, middleware, разделение прав и принцип наименьших привилегий; итог раздела называет JWT. Это не отменяет более конкретное требование задания про Bearer API Key. Уточнить, ожидаются ли JWT или разные права, если это существенно для решения.

Ключ клиента для **нашего API** и ключ доступа сервиса к **CoinMarketCap API** — разные секреты и не должны смешиваться.

### 3.2. Отслеживаемые валюты

- **[Задание]** Предоставить CRUD списка отслеживаемых криптовалют: создание, чтение, изменение и удаление.
- **[Задание]** Для каждой записи хранить как минимум: уникальный идентификатор записи, символ (например, `BTC`, `ETH`, `SOL`), название, дату и время последнего обновления.
- **[Открыто]** Начальный список валют не задан; примеры символов не являются обязательным предзаполнением или исчерпывающим перечнем.
- **[Решение]** Каталог валют хранится локально и используется для поиска по текстовым полям; отслеживаемые валюты и собранные цены хранятся отдельно. CMC ID — единственный идентификатор валюты в API и БД: он хранится в `cryptocurrencies.id`, ссылки на него — в `cryptocurrency_id`; отдельный внутренний ID валюты не нужен. Ориентир модели — [`001-initial.sql`](./src/database/migrations/001-initial.sql).
- **[Открыто]** Для части маршрутов ещё нужно определить правила ошибок и пагинации.
- **[Открыто]** Не определено, означает ли время последнего обновления изменение записи, последнюю успешную синхронизацию цены либо оба события.

### 3.3. Актуальная цена и история

- **[Задание]** Получать актуальные цены отслеживаемых криптовалют из CoinMarketCap API и предоставлять их через собственный API.
- **[Задание]** Сохранять историю цен в БД и предоставлять историю выбранной криптовалюты.
- **[Задание]** Для записи истории хранить как минимум криптовалюту, цену и дату/время получения цены.
- **[Задание]** Валюта цены едина для всего приложения; USD приведён как пример, а не обязательное значение.
- **[Решение]** Валюта котировки задаётся через ENV и записывается вместе с каждой ценой; при смене ENV старые записи сохраняют исходную валюту. `latest` читает последнюю сохранённую цену в текущей валюте ENV из БД; до первой успешной синхронизации такой цены может не быть. `historical` возвращает накопленные нами записи с их валютой котировки, включая прежние валюты.
- **[Решение]** Цена представляется как JavaScript `number`, SQLite `REAL` и JSON `number` в API; точность приближённая. Обоснование и ограничения — [ADR 0001](./ADR/0001-price-representation.md).
- **[Решение]** При отсутствии сохранённой цены `latest` возвращает валюту с `price: null`. Сохранённые даты отдаём в UTC; границы истории принимают ISO 8601 UTC с `Z`, включительно. **[Открыто]** Допустимость нулевой цены, правила отображения и допустимая давность актуальной цены.
- **[Решение]** При добавлении валюты запрос к CMC не выполняется; цены обновляются только фоновой задачей. **[Открыто]** Сортировка, фильтрация по датам, пагинация и срок хранения истории.

### 3.4. Фоновая синхронизация

- **[Задание]** Автоматически и регулярно обновлять цены в фоновом режиме и сохранять историю.
- **[Задание]** Корректно останавливать фоновые задачи при `SIGINT` и `SIGTERM`.
- **[Решение]** Приложение работает в одном процессе; использовать флаг, предотвращающий наложение запусков синхронизации друг на друга. Интервалы задаются отдельно через ENV: по умолчанию обновление каталога каждые 24 часа, цен — каждые 5 минут.
- **[Решение]** Синхронизация цен запускается сразу после запуска сервера и затем по `PRICE_SYNC_INTERVAL_MS` (по умолчанию 300000 мс). Найденные котировки сохраняются, пропущенные ID логируются; ошибка запроса не сохраняет частичный результат запуска. При остановке активный запрос отменяется. Флаг в памяти достаточен только в рамках выбранной однопроцессной модели.
- **[Материалы]** Использовать отдельный слой планировщика с явно переданными зависимостями; встроенные `setTimeout`/`setInterval` подходят без отдельной библиотеки. Очищать активные таймеры, обрабатывать ошибки и фиксировать успешные и неуспешные запуски. Хранение статуса в БД и алерты приведены как варианты мониторинга, не как прямое требование задания.
- **[Предложение]** При остановке прекратить планирование и контролируемо завершить либо отменить активную работу. Точную политику зафиксировать в реализации.

## 4. Контракт API

- **[Задание]** REST API и документация OpenAPI 3.0; входные данные обязательно валидируются.
- **[Материалы]** Ресурсные URL, HTTP-методы и осмысленные статусы; OpenAPI описывает маршруты, методы, параметры, модели, ответы, статусы и схему аутентификации. Stateless-подход; обработка доступа через middleware.
- **[Материалы]** `/status` используется как базовый учебный маршрут, но в самом задании не указан как обязательный.
### Решённые маршруты

**[Решение]** Общий формат ответа — оболочка CMC `status` + `data`, остальное упрощённо; точный контракт полей и ошибок ещё нужно определить. Маршруты нашего сервиса, а не утверждение о доступности таких же маршрутов у CMC:

| Метод и путь | Назначение |
|---|---|
| `GET /v1/cryptocurrency/map?q=&start=&limit=` | Поиск в локальном каталоге |
| `GET /v1/cryptocurrency/tracked?start=1&limit=100` | Список отслеживаемых валют |
| `POST /v1/cryptocurrency/tracked` с телом `{ "id": ... }` | Добавление валюты |
| `DELETE /v1/cryptocurrency/tracked?id=` | Удаление из отслеживания с сохранением истории |
| `PATCH /v1/cryptocurrency/tracked?id=` с телом `{ "is_active": false }` | Приостановка или возобновление отслеживания |
| `GET /v1/cryptocurrency/prices/latest?id=[]` или `?slug=[]` | Актуальные цены |
| `GET /v1/cryptocurrency/prices/historical?id=[]` или `?slug=[]` с `time_start`, `time_end`, `count` | Собранная сервисом история цен |
| `GET /health` | Мониторинг и Docker healthcheck |
| `GET /` | Одностраничный UI: поиск, управление отслеживанием, текущие цены и история с графиком |

**[Решение]** `id` — CMC ID; списки передаются через запятую (`?id=1,1027` или `?slug=bitcoin,ethereum`). Одновременно передавать `id` и `slug` нельзя; ошибка валидации — `400`.

**[Решение]** Для списка отслеживания `start` — позиция с 1, `limit` — от 1 до 100; значения по умолчанию — 1 и 100, порядок — по CMC ID. `PATCH` принимает только boolean `is_active`; `DELETE` удаляет запись отслеживания, но не историю цен. Повторное добавление после удаления допускается. Ошибки некорректного ввода — 400, отсутствующей записи — 404.

**[Решение]** `latest` и `historical` принимают от 1 до 100 разных ID либо slug; при неоднозначном slug возвращается 409. Данные доступны по валютам каталога, включая удалённые из отслеживания. `latest` возвращает последнюю сохранённую цену только в текущей `QUOTE_CURRENCY`; отсутствующая цена обозначается `null`. `historical` возвращает записи во всех сохранённых валютах котировки, по убыванию `fetched_at` и ID записи; `count` — общий лимит от 1 до 1000, по умолчанию 100. `time_start` и `time_end` — включительные границы в UTC ISO 8601 с `Z` и точностью до миллисекунд. HTTP-запросы не обращаются к CMC.

## 5. Архитектура и технологии

### 5.1. Стек и ограничения

**[Задание]**

- Node.js 18+, Express.js, TypeScript. **[Решение]** Сохранять совместимость именно с Node.js 18; версии зависимостей и инструменты выбирать с учётом этого.
- SQLite, только raw SQL; ORM (в том числе Sequelize, TypeORM и Prisma) запрещены.
- Jest и Supertest для тестирования; Swagger / OpenAPI 3.0 для документации; axios для работы с внешним API; Git.
- Docker и docker-compose приветствуются, но не обязательны.
- Данные приложения должны храниться в БД, а не в памяти; файл БД не должен храниться в репозитории.
- Разрешены только указанные библиотеки и стандартные возможности Node.js. Если ограничения делают решение невозможным, предложить своё решение с обоснованием.

**[Решение: зависимость]** Использовать `better-sqlite3` как драйвер SQLite с raw SQL, без ORM. Обоснование отклонения от списка библиотек: для работы с обязательной SQLite нужен интерфейс к БД; в Node.js 18 встроенного `node:sqlite` нет, а разработка собственного драйвера несоразмерна тестовому заданию. `better-sqlite3` — поддерживаемый драйвер с параметризованными запросами и транзакциями; распространённый пакет `sqlite3` объявлен неподдерживаемым. Выбранную версию драйвера и её совместимость с минимальной версией Node.js нужно проверить. Драйвер синхронный, поэтому длительные запросы блокируют event loop. Это обоснование не заменяет разрешения проверяющих; его следует также привести в README.

**[Решение: зависимость]** Использовать `dotenv` для удобной локальной загрузки `.env`: Node.js 18 не загружает его автоматически. Это дополнительная зависимость вне списка задания; обоснование не заменяет согласования с проверяющими. Настоящие переменные окружения имеют приоритет; `.env.example` не содержит секретов.

**[Решение: зависимость разработки]** Использовать `tsx` для `npm run dev`: запуск TypeScript и перезапуск сервера при изменениях без отдельной ручной сборки. Это удобство разработки, а не обязательный компонент production; дополнительную зависимость необходимо обосновать или согласовать.

Также не названы конкретные пакеты для TypeScript/Jest-интеграции и Swagger UI. Не считать их автоматически разрешёнными: уточнить у проверяющих либо явно обосновать минимально необходимые зависимости. Для OpenAPI сам файл спецификации можно предоставить без предположения, что Swagger UI обязателен.

**[Уточнение]** Запрет хранения данных приложения в памяти не следует автоматически трактовать как запрет на локальные переменные, временную обработку запросов или идентификаторы таймеров. Постоянное состояние и история не должны зависеть только от памяти процесса. Допустимость in-memory SQLite для тестов отдельно не оговорена.

### 5.2. Слои и зависимости

- **[Материалы]** Разделение ответственности (SoC), модульность, базовые принципы SOLID — особенно единственная ответственность и инверсия зависимостей.
- **[Материалы]** Разделить обработку HTTP, бизнес-логику, доступ к данным, конфигурацию и утилиты; направление зависимостей — от внешних интерфейсов к бизнес-логике.
- **[Материалы]** Выделить интеграцию с внешним API и планировщик; передавать им БД/репозитории, конфигурацию и логирование явно.
- **[Материалы]** Для доступа к БД рекомендуется Repository Pattern: инициализация БД, инъекция репозиториев в сервисы и преобразование SQL-ошибок в ошибки приложения.
- **[Материалы]** Использовать асинхронный ввод-вывод и не блокировать event loop долгой работой; в учебном проекте для асинхронного кода предлагается `try/catch` с `async/await`.

### 5.3. Модель и целостность данных

- **[Задание]** Сохранять обязательные поля валюты и истории из разделов 3.2–3.3 в SQLite.
- **[Материалы]** Спроектировать отдельные сущности, атомарные поля и ограничения целостности: первичные ключи, необходимые `NOT NULL`/`UNIQUE`, при необходимости внешние ключи.
- **[Материалы]** Использовать параметризованные SQL-запросы для защиты от SQL-инъекций. Многошаговые изменения, требующие атомарности, выполнять в транзакции с `COMMIT`/`ROLLBACK`.
- **[Материалы]** Для дат приведены варианты ISO 8601 в `TEXT` или Unix timestamp в `INTEGER`; конкретный формат не предписан.
- **[Решение]** Начальная схема с каталогом, отслеживанием и историей находится в [`001-initial.sql`](./src/database/migrations/001-initial.sql). При создании БД схема применяется в транзакции и отмечается через `PRAGMA user_version = 1`; неподдерживаемые версии и непустые БД без версии отклоняются. Дальнейшие миграции и политики обновления каталога требуют определения.

### 5.4. Внешний API и устойчивость

- **[Задание]** Использовать официальный CoinMarketCap API и API Key; передавать ключ через переменные окружения. Не хранить его в исходном коде и не передавать клиенту.
- **[Задание]** Внешние запросы должны иметь таймауты и обработку ошибок, включая недоступность API.
- **[Материалы]** Обрабатывать сетевые и протокольные ошибки, изменения формата и некорректные ответы; валидировать, преобразовывать и нормализовать внешние данные.
- **[Материалы]** Рекомендуются retry с задержкой, учёт квот и rate limits, кэширование и graceful degradation; пул соединений рассматривается для высокой нагрузки. Конкретные политики и значения в задании не заданы. В случае хранения кэша учитывать требование сохранять данные приложения в БД.
- **[Открыто]** Конкретный endpoint CoinMarketCap, доступность функций в выбранном тарифе, квоты, таймауты, retry, допустимая устарелость и поведение при отсутствии данных нужно проверить и определить; в материалах они не зафиксированы.

### 5.5. Ошибки, безопасность и наблюдаемость

- **[Задание]** Валидировать все входные данные и обрабатывать ошибки внешнего API.
- **[Решение]** Логирование по методичке с уровнями `error`, `warn`, `info`, `debug` и `trace`; для штатной работы ориентир — `error`, `warn`, `info`, подробные уровни — для диагностики.
- **[Материалы]** Рассмотреть типизированные/кастомные ошибки с контекстом и централизованную обработку; логирование должно помогать диагностике, включая ошибки фоновых задач. Упоминается корреляционный идентификатор запроса.
- **[Предложение]** Не включать секреты и заголовок авторизации в логи и ответы; для клиента использовать согласованный безопасный формат ошибки, не раскрывая внутренние детали.
- **[Открыто]** Не заданы формат и хранение логов, метрики, request ID, модель развёртывания и требования к TLS.

## 6. Тестирование и критерии приёмки

### 6.1. Обязательный минимум

**[Задание]**

1. Каждый реализованный эндпоинт покрыт минимум одним позитивным и одним негативным тестом.
2. Тесты покрывают фоновые задачи и обработку ошибок внешнего API.
3. Используются Jest и Supertest; присутствуют исходный код, инструкция по запуску, описание API и Swagger/OpenAPI-документация.
4. Выполнены требования по CRUD, ценам и истории, Bearer API Key, валидации, хранению в SQLite, таймаутам и обработке ошибок внешних запросов, завершению по обоим сигналам и ограничениям стека.

### 6.2. Практика из материалов

- **[Материалы]** В тестах мокать внешние зависимости, например внешние API, но не мокать БД: проверять реальную цепочку от команды/HTTP-запроса до результата.
- **[Предложение]** Проверить отсутствие/неверность ключа, некорректный ввод, отсутствие ресурса, дубли, SQL-инъекции, таймаут и ошибку CoinMarketCap, некорректный внешний ответ, сохранение истории, поведение планировщика при сбоях и остановку по `SIGINT`/`SIGTERM`. Точный набор зависит от выбранного контракта.
- **[Открыто]** Процент покрытия, конкретные тест-кейсы и проверка живого CoinMarketCap API заданием не определены.

## 7. Состав сдачи и процесс

- **[Задание]** Предоставить исходный код, инструкцию по запуску, описание API, тесты и Swagger/OpenAPI-документацию.
- **[Материалы: Fast Track]** Срок — 7 дней с момента входа в курс LMS; скорость также учитывается. С момента вступления до сдачи ежедневно писать в разделе Daily practice платформы, что сделано вчера и что планируется сегодня.
- **[Материалы: деливери]** Результат желательно описывать через конкретное изменение и проверяемый артефакт; не выдавать процесс или незавершённую работу за готовый результат.
- **[Материалы: follow-up]** После разговора с рабочими решениями фиксировать решения, действия, ответственных, сроки при наличии и открытые вопросы. Это правило коммуникации, а не функция сервиса.
- **[Материалы: Fast Track]** В примере дейлика упомянут Binance API; в конкретном задании указан **CoinMarketCap API**. Для реализации ориентироваться на задание.
